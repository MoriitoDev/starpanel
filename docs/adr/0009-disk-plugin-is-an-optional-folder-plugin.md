# The disk Plugin is an optional folder Plugin, and its safety is its own

A disk-usage and cleanup feature is exactly the kind of thing core's built-in seam exists for — `system-stats` is a built-in, it answers in process, and a cleaner needs no HTTP hop to read `statfs`. We are deliberately not doing that, and the reason is that this Plugin removes things. Reclaiming disk is optional in a way that seeing CPU is not: a panel used only as a dashboard must be able to run without the code that deletes files, and an owner must be able to uninstall it by deleting a folder rather than by trusting a build flag. So it lives at `apps/api/plugins/disk-space/` — a folder whose `src/` is its own Go module and whose `backend` is a compiled binary, with no line in core's module.

The consequence that a future reader will otherwise try to undo is that **core cannot vouch for it**. Core never sees a Candidate, never knows what a Plan contains, and cannot tell a legitimate removal from a hostile one; the ZIP import path means anyone who can reach the port can replace this backend with another ([ADR-0007](0007-plugin-import-is-an-upload-of-code.md)). That is the accepted price of optionality, and it is why every rule that makes removal safe lives inside the Plugin: a Plan only ever removes Candidates the Plugin measured itself, a request body is never treated as a path, everything is a Dry Run before it is applied ([ADR-0010](0010-every-plan-is-a-dry-run-first.md)), and the paths that must never be a Candidate are refused in code with a test behind each one. Rejected: a core built-in, which would have put the deletion code in the trusted binary and made the safest version of this feature the least optional one; and a read-only built-in plus an external cleaner, which splits one measured Candidate set across two processes and makes the Dry Run meaningless.
