# Every Plan is a Dry Run first

The cleanup Plugin answers a Plan in two modes over the same Plan: a measure mode that removes nothing, and an apply mode that removes. Applying a Plan that was not first measured is refused by the engine with a 409 — not hidden in the UI, not a disabled button, an error a `curl` gets too. The obvious design is a single confirmation dialog, and it is what every disk cleaner does; we are buying a second round trip with a guarantee, and the guarantee is that nobody, including the panel's own widget, can ask this backend to delete something without seeing what it would delete first.

What makes that worth the ceremony is that for a whole class of Candidates there is **no way to inspect the decision at all**. Docker decides whether an image is dangling, whether a container is stopped, whether a cache entry is unreachable; those rules live in the daemon and change between versions, and the only honest preview of "prune what is unused" is to run the dry run and read what it says. For file Candidates the dry run is cheap and its value is different: it revalidates each one against the fingerprint taken when it was measured, so the owner learns *before* pressing anything that three of twelve files changed since the scan, and the apply step skips those instead of removing a log that is being written to right now. Rejected: a single confirmation dialog (one round trip, and no preview at all for the Categories where the preview is the only defence); a dry run that is merely the default the UI chooses (a guarantee that lives in markup is one CSS change from gone); and a global "I know what I'm doing" switch that bypasses the preview, which would put the one dangerous path behind a preference rather than behind a second look.
